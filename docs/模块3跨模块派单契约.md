# 模块 3 跨模块派单契约

## 版本与边界

- 契约版本：`ridehailing.v1`。
- 源文件：`api/ridehailing/v1/dispatch_contract.proto`。
- 传输方式：内部 gRPC；不暴露 HTTP 路由，不携带用户 Token。
- 幂等键：全链路使用 `dispatch_no`；同一幂等键的重复消息必须返回成功且不重复改变事实状态。

## 模块职责

| 调用方向 | 服务 | 服务端责任 |
| --- | --- | --- |
| 模块 3 → 模块 4 | `VehicleDispatchGatewayService.SendDispatchInstruction` | 模块 4 接收派单指令并保证相同幂等键不重复下发给车辆 |
| 模块 4 → 模块 3 | `DispatchCallbackService.ReportVehicleDispatchResponse` | 模块 3 条件更新派单记录；只接受待确认记录的一次确认或拒绝 |
| 模块 3 → 模块 2 | `OrderDispatchSyncService.SyncDispatchState` | 模块 2 按幂等键记录订单派单阶段，不重复更新订单状态 |

## 状态映射

| 模块 3 记录状态 | 模块 2 同步事件 | 说明 |
| --- | --- | --- |
| 1 待确认 | `ATTEMPT_PENDING` | 指令已由模块 4 接收待投递 |
| 2 已确认 | `ASSIGNED` | 订单已分配车辆 |
| 3 已拒绝或 4 已超时，且仍可重试 | `RETRYING` | 模块 3 将选择未尝试候选车 |
| 3 已拒绝或 4 已超时，且 3 次尝试耗尽 | `EXHAUSTED` | 模块 2 将订单置为派单失败待人工/用户处理 |

## 事实与安全约束

- 模块 4 回调必须同时带 `dispatch_id`、`order_id`、`vehicle_id`，三者必须与模块 3 已存派单记录完全一致。
- `ACCEPTED` 不得附带拒绝原因；`REJECTED` 必须附带非空拒绝原因。
- `responded_at_unix_milli` 必须大于或等于该尝试的 `dispatched_at`。
- 模块 3 应在本地状态成功落库后再通知模块 2；通知失败需使用幂等键重试，不能回滚既有派单事实。
- 地理点是派单指令快照。订单站点资料后续修改不得反向修改已下发指令。
